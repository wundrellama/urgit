# QUESTIONS — CI P2 (opus chair, branch `ci/p2-opus`)

Each box names what was read, what was tried, and what the chair would do under each answer. None of them blocked the build: every stage was built under the stated assumption, and the assumption is the one the record's Deviations name. The operator rules them.

## §1 — A pull request from a non-writer needs a second ship; the rows drive the stage poke instead

**Read.** BRIEF-CI-P2 D3a ("this is where `%untrusted` candidates come from: `source-ship` on a fork PR is not in `can-write`") and rows Q5/Q6/Q8 ("a PR whose `source-ship` is not a writer, merged by a writer"). `urgit.hoon`'s two pull-request constructors: the web `POST /repository/<name>/pulls` route (:7232) records `source-ship = our.bowl`; the peer path (`peer-push-finish`, :2686) records `source.flight`, the poking ship. `can-write:git-access` (:74) admits the owner unconditionally, and every repository this ship creates has `owner = our.bowl`. The footer gives one ship, `~dep`, and forbids the listed galaxies and the other chair's `~lup`; it does not name a second ship for this chair.

**Tried.** A same-ship PR through the web route (Q5a) is always trusted — the route's `repository-writable u.found source-ship.pull` is `%.y` for the owner. No `%git-action` plants a pull with a foreign author; the `%git-peer` poke takes its author from `src.bowl`, which a khan strand cannot forge. So on one ship the only way to a non-writer's revision is the stage poke `%urgit` would send for a fork PR: `[%stage-candidate repo ref head base ~sampel-palnet %session %untrusted ~]`, which Q5, Q6, Q8 and Q10 drive through the dojo (`q5-8.sh`'s `stage_untrusted`). Everything downstream of the poke — untrusted staging, no planning under `%approval`, the `%restricted` run with `grants=~` and no landing, approval by the owner, refusal of any other actor — is exercised live and RED/GREEN. What is not observed live is the one line in the merge route that decides the class, `?:((repository-writable u.found source-ship.pull) %trusted %untrusted)`; its `%trusted` branch is Q5a's and `can-write` itself is `+urgit!git-access-vector`'s.

**Under each answer.** (a) *Boot a second fake galaxy for this chair* (one not on the footer's list, its own HTTP port and pier, `%urgit` installed): the harness gains `q5-peer.sh` — the second ship forks the repository through the peer protocol, pushes a commit to its fork, opens the PR with `POST /peer/pull-request`, and `~dep`'s writer merges it through the web; Q5–Q8 then have a live `source-ship` that is not a writer and the merge route's classification is observed. About an hour of harness work and one more pier; the operator names the ship and ports. (b) *Keep the seam*: the rows stand as recorded; the record's Deviations say so. (c) *A test-only actor override on the merge route* (a body field the route honours only from the ship's own session) — rejected by the chair: a production route that lets the session choose the actor is a hole, not a seam.

## §2 — act 0.2.89 does not mask a multi-line secret; credential values are single-line until ruled

**Read.** BRIEF-CI-P2 §6 names this box ("act's `--secret` masking behavior on multi-line values"). D4: the value "never appears in any … log line"; "act masks secrets in its own output; the daemon must additionally scrub any line containing a grant value before relay".

**Tried.** A probe on the static act 0.2.89 in the harness's rootless Docker (`.scratch/tmp/keep-actprobe-secret.yml`, output `keep-actprobe-secrets.jsonl`): two secrets, `ONE=single-secret-value` and `MULTI=alpha-line-1\nbeta-line-2`, each echoed by a step and written to `$GITHUB_OUTPUT`.
- Single line: the echo is masked (`"msg":"one is ***\n"`), the set-output **msg** is masked (`::set-output:: one=***`) but the set-output line's **`arg` field carries the raw value** (`"arg":"single-secret-value"`). The ship's scrub of set-output values (`scrub:ci-event`, applied in `handle-event` before `record-output`) and the daemon's line scrub both exist because of this line.
- Multi-line: nothing is masked. Each line prints in clear (`alpha-line-1`, `beta-line-2`, `second line alone: beta-line-2`), and the output carries `alpha-line-1_beta-line-2`. act masks a secret only where the whole value occurs on one output line; a value printed line by line never matches. The daemon's whole-value scrub and the ship's have the same blind spot.

**Built.** `%set-credential` refuses a value containing a newline (`'credential values must be a single line'`) and the settings form refuses it before posting. A multi-line credential (a PEM key, a JSON service account) therefore cannot be stored in P2.

**Under each answer.** (a) *Keep the refusal* (the chair's default): documented as a limitation; operators base64-encode multi-line material and decode it in the step. (b) *Scrub per line*: the daemon and the ship add every line of every released value (of at least eight characters) to the scrub set, so a line-by-line print is masked; act's own masking stays as it is. A one-line change on each side plus a vector each; the refusal is lifted. (c) *Carry a patched act*: the spec allows "small patches may be carried in-tree", but an act change is a daemon change with a parity run, and P2 pinned 0.2.89.

## §3 — "A writer approves" is this ship's owner; a `can-write` read for approvals needs a fourth `%urgit` touch

**Read.** D3 ("(b) a writer approves it"), Q8 ("approval by a non-writer → refused"), and the fence ("exactly three touches" in `urgit.hoon`; "nothing else"). `%urgit-ci` has three reads of `%urgit` (`/ci-ref`, `/ci-tree`, `/ci-file`) and none answers whether a ship can write a repository; the public repository JSON peek hides `writers` and answers `[~ ~]` for a private repository, which kills the reading event.

**Built.** `%approve-candidate id actor` refuses every actor but `our.bowl`. In P2 that is exactly the set of writers that can reach the poke: the `%ci-action` poke requires `src.bowl = our.bowl`, `POST ci/action` sets the actor to the session's ship, and the owner writes every repository it holds. The trust class at staging is decided by `%urgit` (which has `repository-writable`) and carried in the stage poke; the receive-pack path passes `%trusted` (its admission is `write-authorized`).

**Under each answer.** (a) *Keep it*: correct for every actor P2 can produce; recorded in Deviations. (b) *A fourth touch*: `on-peek` in `urgit.hoon` gains `[%x %ci-writer @ @ ~]` → `?` (the shape of P1's `ci-ref`), and `%urgit-ci` evaluates `can-write` itself for approvals and for any stager that names an actor, so a listed writer or a `%write` group member could approve once a route lets them act; `%stage-candidate` could then drop its `trust` field. The chair did not make the touch because the fence forbids it and no reachable actor needs it in P2.
